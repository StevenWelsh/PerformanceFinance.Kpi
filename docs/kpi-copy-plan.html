KPI copy plan

How the KPI figures get from CMS_Live in the office to the KPI website in Azure (kpi.performancefinance.co.uk): what lives where, how one copy runs, who can read what, and why it is built this way. This is the design as built on 18 October 2026 - a pull, which replaced the earlier plan of a push from the office. The step-by-step switch-on is docs/kpi-pull-runbook.md.

1. The flow

The office does the work on its own schedule; the site only follows. Nothing in the office connects out, and no program of ours runs there: the jobs are plain SQL. The only thing crossing the internet is the site reading finished copies, with a login that can do nothing else.

3. One copy, step by step

  1. In the office, every 10 minutes (07:00-20:00, Mon-Sat): the Agent job runs KpiCopy.spRefresh. It checks CMS_Live's KpiExport.Version, then in one transaction rebuilds every KpiCopy.X from CMS_Live.KpiExport.vX (and the two snapshot tables) and stamps KpiCopy.Refresh. A second refresh started meanwhile gives up at once.
  2. At 00:15: the nightly job runs KpiCopy.spNightly: CMS_Live's KpiExport.spPrepareSnapshots (the desktop's Bad Debt and Exposure, a few minutes), then the same refresh.
  3. In Azure, every 2 minutes: the site reads the one-row KpiCopy.Refresh. If it is newer than CMS_KPI's last publish (Rpt.spDataStatus), it bulk-copies the tables into Stage - with Bad Debt and Exposure if they were prepared since the last nightly publish.
  4. Before publishing it reads the refresh row again: if the office refreshed meanwhile, the tables might come from two refreshes, so nothing is published and the next check copies again.
  5. Stage.spPublish swaps everything into the report tables in one transaction. Figures are at most about 12 minutes behind CMS.

When something fails: nothing is published and the site keeps the last good figures. The card shows Last problem; Settings > Data sync logs the failure once when it starts and then hourly; after 30 minutes in office hours every report says its figures are overdue; in the office, the Agent job history has the error.

5. Versions, and changing CMS

  • CMS_Live.KpiExport.Version (1): the shape of what CMS hands over. spRefresh copies nothing from another version.
  • KPI_Export.KpiCopy.Version (3): the copy side's script. The site copies nothing from another version.
  • Both expected values live in Kpi.Copy/Export/ExportVersion.cs (Cms, Current).
  • Before renaming or dropping anything in CMS, search CMS.Models/Scripts/KpiExport/ (its README has the query listing every CMS column used). SQL Server won't stop the change - the view breaks quietly and the refresh fails. Fix the view in the same CMS migration; if its columns change, raise both versions together.

6. Decisions behind it

DecisionWhy
A pull, not a push (16 Oct)Steve wants a SQL Server data source in his reporting product, as Klipfolio has; nothing in the office needs a password for Azure. The office still never connects out.
Copies in KPI_Export, not the views read directlyOwnership chaining is off on PF-APP1, so reading the views would need rights on CMS_Live's tables (as Klipfolio's Fendra login has). The copies also make each refresh one consistent moment and keep the long read over the internet off CMS_Live.
The views in CMS, the copies outside it (18 Oct)The views name CMS's columns, so they live where a CMS change would break them. The copies (65,000 rows every 10 minutes) stay out of CMS_Live and its transaction log.
SQL Server Agent, not CMS.Scheduler or a programThe work is one stored procedure. Agent runs it inside the server with no exe, no credentials and no CMS release to change it - and it is what starts CMS.Scheduler anyway.
A dedicated static IPApp Service's own outbound addresses (31 of them) are shared with other Azure customers; the office rule should admit PF alone.
No certificate on PF-APP1's SQL Server (for now)The connection is encrypted; without a certificate it can't also verify the server. The address is locked both ways, so Steve chose not to ask PCS for one.

8. Retiring the CMS copy of the KPIs

CMS.Web isn't live, so nobody relies on its /kpis pages. Proposed: once the KPI site is live, remove the KPI area from CMS so the KPI site is the only KPI front end, for the office as well, and replaces Klipfolio. That ends the "change both copies" rule. To be decided - and not before the site has run on live figures for a while.

WhereWhat goesNotes

Each report's calculation already lives in the KPI repo (Rpt.sp* in CMS_KPI, matched 241 of 241 against CMS). Once WebKPI goes there is nothing left to compare with, so the last step before removing it is one final full comparison.
