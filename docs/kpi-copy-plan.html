KPI copy plan

How the KPI figures get from CMS_Live in the office to the KPI website in Azure: what exists, what gets added where, and how one copy runs. Nothing here is built yet; today the site holds a single copy pushed by hand from a developer's PC, out of a local stand-in that reads CMS_Dev.

1. The overall flow

CMS_Live is read through a separate KPI_Export database of views. Kpi.Push, run by SQL Server Agent on the office server, copies those views one way into CMS_KPI in Azure, which the KPI site reads.

2. What gets added where

Grey exists today; teal is to be added. CMS_Live itself does not change: no new schema, views or migrations inside it.

3. One copy run, step by step

Office steps on the left, Azure on the right, in the order they happen.

  • One at a time: Kpi.Push takes a lock first; a run that starts while another is still going simply skips.
  • Nightly only: KpiExport.spPrepareSnapshots calls CMS's own Bad Debt and Exposure procedures and stores the results in KPI_Export.
  • Reading: every KPI_Export view is read as at the same moment, so the figures agree with each other.
  • Copying: each Stage table in Azure is emptied and refilled by bulk copy. The site never reads Stage, so a copy that stops halfway changes nothing on screen.
  • Publishing: Stage.spPublish moves everything into the report tables in one transaction: readers see the old figures until the new ones are complete, never a mix.
  • On failure: nothing is published and the site keeps the last good figures. The failure is logged in Azure (Settings › Data sync) and in the office server's event log; after 30 minutes without a good copy, "As at" turns amber.

4. How it connects to Azure

Everything goes outwards from the office; nothing in Azure can connect in.

StepWhat happens
Sign in to MicrosoftKpi.Push asks Microsoft Entra ID (PF's Microsoft directory) for a sign-in token, proving who it is with a certificate installed on PF-APP1 that belongs to the push identity. No password in any file.
ConnectAn encrypted connection to pf-sql-uk.database.windows.net on port 1433, presenting the token.

RightsIn CMS_KPI the push identity has the kpi_push role only: fill Stage and run the publish. It can't read reports, users or settings.

7. Decisions behind it

QuestionDecision
Views inside CMS_Live, or a separate database?A separate KPI_Export database beside CMS_Live. CMS stays untouched, nothing KPI-specific clutters it, and KPI changes don't need a CMS release.
Migrations for KPI_Export?Not yet. It holds no data that must survive a change (views and procedures are replaced wholesale; snapshots refill nightly), so one rerunnable script in git does the job. Migrations can be added later with no real downtime: pause the two Agent jobs, add a baseline migration equal to the script, resume.
Catching CMS changes that break a viewKpi.Tools export-check after every CMS release, plus the nightly copy failing loudly as the backstop.
Wrong script version on the serverA version stamp in KPI_Export; Kpi.Push refuses to copy from an older one.
Who runs the copy?SQL Server Agent, beside CMS.Scheduler's jobs: KPI copy – frequent (every 10 minutes, 07:00–20:00, Mon–Sat) and KPI copy – nightly. Kpi.Push stays a separate program: modern .NET for the Azure sign-in, versioned with the KPI repo.
How does the copy sign in to Azure?An app registration ("PF KPI Push") with a certificate kept on PF-APP1. Fallback if that drags on: switch on ordinary SQL logins for the server and give the copy a username and password.

8. The request to PF's IT

For the new KPI website, a program on PF-APP1 will copy KPI figures every 10 minutes to our Azure database (outbound only; nothing in Azure connects in). Could you please:

  1. Tell us the public IP address PF-APP1 uses for outgoing internet traffic, and whether it's fixed. We'll add it to the Azure database firewall.
  2. If outgoing traffic from servers is restricted, allow PF-APP1 out to:
    • pf-sql-uk.database.windows.net, TCP port 1433 (Azure SQL, encrypted)
    • login.microsoftonline.com, TCP port 443 (Microsoft sign-in)
  3. Create an app registration in the Performance Finance Entra ID called "PF KPI Push": single tenant, no redirect URI, no API permissions needed. We'll send you a certificate (.cer, public part only) to upload to it. Please send back its Application (client) ID and the Directory (tenant) ID.

9. Order of work

  1. Send the IT request (above). The app registration is the step most likely to take time.
  2. Move the script into Kpi.Push, add the version stamp, and the Kpi.Tools commands export-apply, export-check and grant-push.
  3. Run export-apply --cms CMS_Live on the office server, then export-check.
  4. When IT reply: add the office address to the Azure firewall, the certificate to PF-APP1, and grant-push for the new identity.
  5. Publish Kpi.Push to PF-APP1 and create the two SQL Agent jobs.
  6. One manual run, the 241-report comparison against live CMS, and the site's "As at" showing today's real figures.

CMS.Web isn't live, so nobody relies on its /kpis pages. Proposed: remove the KPI area from CMS before CMS.Web goes live, so the KPI site is the only KPI front end, for the office as well, and replaces Klipfolio. That ends the "change both copies" rule for every KPI change. To be decided.
